What we are actually building

Software cannot edit video it cannot read. So before any Director, Critic, or render step can exist, the footage has to become language — a structured, queryable description of what happens, when, and whether it is any good.

That is this project, and only this project. Ingest one clip, cut it into shots, transcribe it word by word, judge each moment, score the image quality, and emit one validated JSON file. Everything downstream is later.

But there is a second thing happening underneath, and it is the more important one. This repo is one half of a controlled experiment.

Path B — this repo
Gemini-native
  • Understanding One whole-video pass, audio + visual, cross-shot context
  • Cost ~30K tokens per video, free tier
  • Bet Long-context beats frame-by-frame
Path A — co-founder’s repo
Local VLM
  • Understanding moondream2, one keyframe per shot, on-device
  • Cost Local compute, no API
  • Bet Nothing leaves the laptop

Shot cuts, transcription, and quality scoring are identical on both sides — same library, same settings. Both emit the same schema. So the only variable left is Understanding, and the diff between the two output files on the same footage is the architecture decision.

What exists when this is done

A working command

python -m elvideo index in.mp4 produces a schema-validated index in under five minutes, on a laptop, on a free API key. No cloud account, no GPU cluster, no upload form.

An answer, with evidence

Two indexes of the same footage, one per path. Where they agree, the pipeline is sound. Where Path B fills in editorial_score and moment_reason and Path A cannot — that gap is the measurement.

A locked contract

One JSON Schema both repos build against. Merging the two efforts becomes a twenty-minute conversation instead of a refactor, because neither side ever diverged.

A foundation, not a demo

The index is the substrate every later stage reads. Director picks shots from it, Critic judges cuts against it, search queries it. Stage 1 done properly is what makes stages 2 through 5 tractable.

What you will not have

  • No rendered video. Nothing is cut, trimmed, or exported — this reads footage, it does not edit it.
  • No UI. One CLI command, one file at a time.
  • No Director, Critic, or Delivery agents.
  • No embeddings or semantic search. The field is reserved in the schema and stays null.
  • No cloud storage. Local filesystem only; the clip sits in Google’s File API for 48h during processing and nowhere else.

Feeding it a 10-minute video

Say a 10:00 clip of small-business b-roll — a restaurant kitchen, vertical 1080×1920, roughly 140 cuts, someone talking over most of it. You run one command and walk away. Here is what happens, and where the time goes.

Drawn to scale except probe and build, both sub-second. These are estimates, not measurements — T009 replaces them with real numbers. The biggest risk to the budget is transcription on CPU rather than GPU, which can multiply that 90s several times over.

1
Probe probe.py ffprobe <1s

Reads duration, frame rate, and pixel dimensions. Cheap, and it fails fast — if ffmpeg is missing or the file is corrupt, you find out in a second rather than after two minutes of transcription.

in.mp4 → 600.0s · 29.97fps · 1080×1920
2
Cut into shots scenes.py PySceneDetect ~45s

Walks all 18,000 frames looking for content changes and returns frame-accurate boundaries. These timings are load-bearing: every later stage indexes off them, and they are the only numbers precise enough to cut on.

18,000 frames → ~140 shots → shot_000 … shot_139
3
Transcribe every word transcribe.py WhisperX ~90s

Not sentence-level subtitles — per-word timings. That is what makes it possible later to cut on a syllable, strip an “um”, or find the exact frame someone says a product name. The slowest stage, and worth it.

audio track → ~1,400 words → { t: 42.10, d: 0.22, w: "so" }
4
Watch the whole thing, once gemini.py gemini-3.5-flash ~75s

The clip goes up to the File API, and one request asks the model to watch all ten minutes — frames at 0.5fps plus the audio — and return structured JSON: what each shot shows, how strong a moment it is from 0 to 1, why, and tags.

Because it sees the whole video in one context, “how strong a moment” means relative to everything else in this clip. A per-shot captioner cannot express that at any price.

300 sampled frames + audio → 1 request → ~140 judgments
5
Score the image quality quality.py OpenCV ~15s

Pulls one keyframe per shot and measures focus and exposure with a Laplacian. No model, no opinion — the same pixels always give the same number. A gorgeous composition that happens to be out of focus scores high on judgment and low here, which is exactly the distinction an editor needs.

140 keyframes → quality: 0.79
6
Join, validate, write build.py orchestrator ~2s

Merges the model’s judgment onto the frame-accurate shot list, slices the word stream into per-shot transcripts, flags the strong moments, and checks the whole document against the shared schema before writing. A run that fails validation leaves no file behind rather than a plausible-looking broken one.

5 streams → work/footage_index.json → ~100 KB

Why one call, and not one per shot

140
calls, the naive way
One per shot. At the free tier’s 10 requests/minute that is 14 minutes of waiting before any work happens — and it exhausts the daily quota on a single video.
1
call, this design
The whole clip, once. Well inside every rate limit, and the model gets to compare shots against each other instead of judging each in isolation.
~30K
tokens per video
300 frames at 66 tokens each (media_resolution: low) plus audio, against a 250K-per-minute cap. Cheap enough to re-run all day while tuning the prompt.

This is a product decision, not an optimization. A design that drifts back toward per-shot calls is wrong even if it runs — it throws away the cross-shot reasoning that is the entire reason to take Path B.

What the model decides, and what it never touches

The split that keeps this honest: the model is asked for judgment, never for measurement. Anything that has to be exact or reproducible is computed classically. Gemini's own timestamps are only accurate to the second — useless for cutting — so they are used for nothing but matching its output to the real shots.

FieldDecided byWhy it sits there
t_start, t_end PySceneDetect Frame-accurate. The model’s guesses are second-granular.
transcript WhisperX Word-level timing drives precise cuts and filler removal.
quality OpenCV Must be reproducible across runs and across both A/B paths.
caption Gemini Describing what is happening is judgment.
editorial_score Gemini How strong a moment, 0–1. The whole point of Path B.
moment_reason Gemini The justification behind the score — evidence, not decoration.
tags Gemini Informed by the whole video, not one frame.
is_candidate derived A threshold over editorial_score, not a separate answer.
embedding reserved Stays null. Exists so Phase 2 is not a schema break.

What lands on disk

One file, roughly 100 KB, containing every shot — not a curated top ten. “Best moments” is a filter you apply later, which is what keeps both A/B paths emitting the identical shape.

Which makes questions like these cheap

“Find me the three strongest food shots with clean audio.”
filter is_candidate & tags ∋ food & transcript ≠ "" → sort editorial_score → take 3
“Where does she say ‘brunch’?”
scan words[] → t = 44.8 → the shot whose range contains it
“Give me only usable silent b-roll.”
filter quality > 0.6 & transcript = "" → sort by duration
“Which path described shot 7 better?”
diff caption & moment_reason across the two index files

Every one of those is a filter over text and numbers. No video decoding, no model call, no waiting. That is what the index buys.
